## Batch arithmetic and why it matters

Upstream's new scheduler divides cache-missed experts in *batch rows mode*, not ordinary single-request prefill. The CPU still calls the same legacy `cpu_moe::expert_rows` function. It is not a fix for the numerical contract proven divergent by R4/R8/R9. Moreover, the previous fork had a distinct `rows.is_some()` branch that selected every missed expert for CPU even when R4 was off. That branch bypassed the ordinary-prompt R4 research gate.

R11U1 closes that bypass for the active PS5 Vulkan profile (`g.ps5_preset()`). All missed experts in this batch path stay in the existing GPU staging path. `STRATA_CPU_FRAC=1` cannot enable batch CPU execution there, nor can R4's research switch. Optional `STRATA_PS5_U1_BATCH_LOG=1` reports actual per-layer staged/CPU counts in batch mode only. This does **not** modify the usual single-request prefill route, the existing single-token decode CPU mailbox, or the diagnostic R4 opt-in prompt experiments. It is not a claim that all CPU experts in every inference path have been disabled. GPU staging may cost more time or memory than the former batch CPU route; this behavior needs physical validation, especially with very low residency. Keep R11 for reference and do not claim a throughput win from U1.

For other profiles, adopt upstream's 0.5 starting share, whole-expert partition, concurrency and +/-0.02 adaptation. A fixed `STRATA_CPU_FRAC` must be finite and in [0,1]; reject malformed/out-of-range values rather than risk invalid split indices. Fixed 0 selects none. Adaptive rounding always samples at least one missed expert, so a zero share cannot permanently starve feedback. Measure completion using `beside_join`, `kick`, `sync` before joining/scattering, rather than equating CPU submission latency with GPU execution. This deliberate extra completion boundary may cost performance on desktop; benchmark separately. Scoped thread is joined on errors. The ordinary R4 prompt path retains its exact code and separate policy. No non-PS5 hybrid quality claim either.

## Deferred changes

- Upstream multi-device `step_batch`/`prefill_slots` extension and its split test are not adopted. PS5 target is one device; enabling this feature would require checking eligibility and batch capacity of *all* parts, mixed dense/recurrent partitions, row-table lifetime and position accounting. In the supplied upstream, `batch_cap()` checks that every part has a batch object but returns the first part's capacity, not their minimum. Its path decision is based on the first part's `dense` flag while final dense dispatch can refer to the tail. These are static concerns, not reproduced failures. Do not relax the fork's single-device scope solely to achieve byte-for-byte upstream parity.
- Do not replace the existing strict `batch_matches_single`/`prefill_slots_matches_single` assertions with the new upstream mean-distance-to-CPU acceptance test. It can be useful as an additional diagnostic in a separate campaign, but not as the gate for our GPU/CPU equivalence. The CPU reference itself is not the GPU arithmetic contract.
- No new vision/Vulkan changes exist in the supplied incremental upstream source. No new IQ, R4 or MTP candidates are promoted. TurboQuant and host attention policy unchanged. R3/R4 quarantine and R9/R10 controls stay intact.
